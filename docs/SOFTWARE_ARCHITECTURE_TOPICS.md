# `sigcon` 软件架构设计与落地规范

## 1. 核心架构原则

本规范定义了 `sigcon` 软件部分的架构标准，旨在构建一个高内聚、低耦合、具备强防御性编程能力的系统。

### 1.1 主控制链与依赖方向
- **单向主控制链**：`UI <-> 调度 <-> 业务`
- **双盲隔离**：`UI` 层不知道业务的存在，业务层不知道 `UI` 的存在。两者绝对禁止直接交互。
- **唯一枢纽**：调度层是唯一合法的编排层，负责组织 `UI` 与业务的连接。
- **依赖拓扑禁忌**：架构中绝对禁止出现**三角依赖**和**菱形依赖**。系统依赖必须尽量保持无环，禁止横向穿透破坏主控制链。

### 1.2 状态与资源管理
- 一份核心状态不能被多条路径并行主写。
- 一个核心实例不能被多个装配入口重复创建和并行管理（向下严格管理）。

### 1.3 配置更新总原则
- 配置更新链路统一采用 `upconfig` 和 `setconfig` 两级接口语义，禁止各模块自行发明同义接口名。
- `setconfig` 是单元自我生效接口，负责当前单元内部状态、参数、UI 表现的更新。允许空实现，但绝对不能缺失。
- `upconfig` 是调度链更新接口，负责接收配置变更、协调当前层刷新、并向下级继续分发。
- `UI` 模块和业务模块都必须提供 `setconfig`，因为配置变更不仅影响界面字体，也可能影响任务参数、执行规则、阈值和设备策略。
- 配置更新必须保持单向自上而下传播，禁止下级绕过直属上级直接改写其他分支配置。

## 2. 四层调度理论体系 (L0 ~ L3)

调度层不是单一的“垃圾桶”，而是采用树状分工的四层调度体系。高层负责装配与生命周期，底层负责具体执行，**低层绝不能反向持有或越级承担高层职责**。

* **L0 (最小逻辑单元)**：负责最基础、单次、结果唯一的调度行为（如单次格式化指令）。不允许创建多线程，不负责窗口装配。
* **L1 (最小功能单元)**：负责单一窗口、页面的调度闭环。负责将页面交互转成业务调用，再将结果转成页面状态。接管警告级局部异常，保护页面不崩溃。
* **L2 (最小业务单元)**：模块级/业务域级调度器。负责多步骤流程编排与 L1 的切换。负责业务断点时的重试或流程回滚。L2 内必须存在固定配置模块，专门负责配置的读取、写入、暂存和合法性校验，但不负责全局立即生效。
* **L3 (最小软件单元)**：应用级总装配根。负责应用全生命周期管理。**全系统唯一拥有多线程/多进程创建与回收权的地方**。L3 向下装配 L2 和 L1，并作为全局致命异常的最后兜底网。同时，L3 是全局配置应用入口：当用户在 L2 完成配置编辑并按下“生效/确定”后，由 L2 通知 L3，随后由 L3 发起全局 `upconfig`，逐层向下调用各单元的 `setconfig`。

## 3. 标准物理文件架构

为了在物理层面锁死依赖关系，整个工程的目录必须严格按照以下结构划分。同级目录之间绝对物理隔离。

```text
Project_Root/
├── assets/                    # 【静态资源域】图片、图标、样式表、多语言翻译包
├── config/                    # 【配置资产域】默认配置、配置模板、配置说明、配置版本定义
├── data/                      # 【运行数据域】缓存、数据库、导出结果、临时文件、运行期产物
├── docs/                      # 【文档域】架构说明、API协议、错误码对照表
├── lib/                       # 【第三方库域】(绝对隔离，禁止业务/UI直接引用)
│   ├── spdlog/                # 第三方日志库
│   ├── nlohmann_json/         # 第三方 JSON 库
│   └── ...                    
│
├── src/                       # 【核心源码区】
│   │
│   ├── ui/                    # 模块一：【纯 UI 层】(只能依赖 support，盲区：不知道业务和调度)
│   │   ├── components/        # 基础公共组件 (如：无业务逻辑的自定义按钮)
│   │   ├── panels/            # 局部业务面板 (如：状态显示面板，只抛出交互信号)
│   │   └── windows/           # 独立顶层窗口 (如：主窗口、设置弹窗)
│   │
│   ├── business/              # 模块二：【纯业务层】(只能依赖 support，盲区：不知道 UI，禁止弹窗)
│   │   ├── device_ctrl/       # 业务域：设备控制
│   │   │   ├── exceptions/    # 局部异常定义：如 DeviceException.h
│   │   │   ├── models/        # 数据模型：纯 C++ struct/class
│   │   │   └── DeviceManager.cpp 
│   │   └── algorithm/         # 业务域：核心算法
│   │
│   ├── scheduler/             # 模块三：【调度层】(中枢：唯一允许同时 import UI 和 Business 的地方)
│   │   ├── l0_action/         # L0 动作编排
│   │   ├── l1_page/           # L1 页面调度：组装 UI Window + 基础动作
│   │   ├── l2_domain/         # L2 业务调度：组装 L1 + Business (处理重试/中断，并承载配置读写模块)
│   │   └── l3_app/            # L3 软件装配：全局控制台、全局配置应用入口
│   │       ├── thread_pool/   # 【核心管控】多线程独占区：全项目唯一定义后台 Worker 的地方
│   │       ├── app_context/   # 全局运行时上下文
│   │       └── main_entry.cpp # 启动与兜底：向下装配 L2；全局 try-catch 收口
│   │
│   └── support/               # 模块四：【支撑域】(基石：被上层单向依赖，禁止反向 import 上层)
│       ├── core/              # 核心规则区 
│       │   ├── exceptions/    # 全局异常基类：AppBaseException.h (定义错误码、重试策略)
│       │   ├── constants.h    # 全局常量、协议键名
│       │   └── shared_state.h # 极少量的、严格受控的全局状态
│       │
│       ├── infra/             # 基础设施区 (第三方库的“防腐层”)
│       │   ├── logger/        # 封装日志库 (业务层只能用这里的 AppLogger::info)
│       │   ├── storage/       # 封装本地缓存/数据库
│       │   └── ipc_network/   # 封装多进程/网络底层通信
│       └── utils/             # 纯函数工具箱 (时间、字符串、校验等)
```

### 3.1 配置文件与运行数据边界
- `config/` 只存放项目认可的配置资产，如默认配置、模板、配置键定义、版本说明，不承担业务运行期数据堆放职责。
- `data/` 只存放运行过程中产生的数据，如缓存、数据库、导出文件、任务中间产物、运行日志。
- 用户运行后形成的实际配置快照，如确需持久化，应视其用途决定归属：作为模板或默认值归 `config/`，作为运行期覆盖值归 `data/`。

### 3.2 配置传播规则
- 用户在界面编辑配置时，L1 只负责交互采集，具体读写由 L2 配置模块负责。
- 用户按下“生效”或“确定”前，配置允许停留在 L2 的暂存态，不要求全局立即刷新。
- 用户按下“生效”或“确定”后，必须由 L2 通知 L3，由 L3 作为唯一全局入口发起 `upconfig`。
- `upconfig` 负责逐层分发，`setconfig` 负责本单元落地，禁止把“读取配置文件”“全局生效”“局部刷新”混成一个接口。

## 4. 异常防御与流转机制

贯彻“防御性编程”与“零信任”原则，异常体系必须基于元数据驱动，而非类名硬编码。

### 4.1 异常基类设计 (`AppBaseException`)
所有异常必须派生自 `support/core/` 下的统一基类，基类必须携带以下元信息：
* **错误码 (`errorCode`)**：统一错误字典定义。
* **严重等级 (`level`)**：`FATAL`(崩溃), `ERROR`(局部失败), `WARN`(可忽略)。
* **处理策略**：`shouldRetry` (是否允许重试)，`shouldShowToUser` (是否弹窗提示)。
* **信息隔离**：`developerLog` (含堆栈，写入本地日志)，`userMessage` (友好的用户提示)。

### 4.2 预期错误与崩溃的分离
* **Result 模式**：用于预期内的业务分支（如搜索不到设备、密码错误），不抛异常。
* **Exception 模式**：用于预期外的崩溃（如断网、文件损坏、断言失败），直接抛出。

### 4.3 异常流转接力赛
1.  **抛出点 (底层)**：业务层或基建层遇到致命错误直接抛出派生异常，**绝对不处理用户提示**。
2.  **微调点 (L1)**：捕获 `WARN` 级异常，转换为界面红字/黄牌警告，拦截异常防止页面崩溃。
3.  **恢复点 (L2)**：捕获 `ERROR` 级异常，根据 `shouldRetry` 执行模块级重连或流程回滚。
4.  **兜底点 (L3)**：捕获所有遗漏的 `FATAL` 异常。记录崩溃日志，弹出全局致命错误框，安全释放多线程资源后退出。

## 5. 多线程与多进程并发模型

为了确保 UI 主线程安全并解决异步数据投递问题，系统采用以下并发管理模型：

### 5.1 依赖反转与契约通信
业务层（包括独立的网络线程或 IPC 通信进程）绝对禁止直接调用调度层或 UI。
数据返回必须通过**标准契约**：即回调注入（`std::function`）或发布/订阅（信号与槽机制）。业务模块只负责“无脑”触发回调，不关心数据去向。

### 5.2 多线程/进程创建权管控
* 进程的 `fork`/拉起、以及全局线程池的管理，全部由 **L3 (基础设施/app_context)** 统一提供并掌管生命周期。
* L0/L1/L2 目录下的调度器如果需要异步能力，必须向 L3 申请，严禁私自 `new Thread`。

### 5.3 统一主线程事件序列化 (化解并发冲突)
* **绝对禁止非主线程直接修改 UI。**
* 当后台子进程/子线程通过回调或信号返回数据时，调度层必须将该行为封装为“事件”，压入**主线程事件队列 (Event Loop)**。
* 所有并行到达的任务，在主线程中都会被序列化排队执行，从根本上消灭并发资源争抢。

### 5.4 基于 TaskID 的精确路由
为了将后台进程的结果准确送达对应的 L1 页面：
1.  **发起**：L1 触发任务时，附带唯一的 `TaskID` 交给 L2。
2.  **执行与返回**：底层业务/子进程原路带回 `TaskID`。
3.  **路由分发**：L3/L2 根据内部映射表，将带有特定 `TaskID` 的结果派发给对应的 L1。若 L1 已被销毁，则安全丢弃数据，防止内存崩溃。

### 5.5 生命周期与健康管理
- 一个单元的生命周期必须由直属上一级单元管理，包括创建、持有、替换、销毁和退出清理。
- 下级单元绝对禁止反向接管上级生命周期，也禁止越级销毁兄弟单元。
- 健康管理不采用 L3 对全树做高频递归深扫的模式，避免递归链过深和扫描负担过重。
- 每个单元只负责自身及直属子单元的健康状态汇总，异常和状态以逐层上报为主，不以顶层全量轮询为主。
- L3 负责全局健康策略、告警和恢复决策，不负责高频细节探测；高频检查优先采用事件上报加低频巡检的混合模式。

## 6. 架构落地的“三大铁律”

此三条作为 Code Review 的一票否决项：

1.  **跨层防腐铁律**：UI 绝不能 `#include` 业务；底层代码绝不能包含任何第三方库的原始头文件（必须通过 `support/infra` 防腐层中转）。
2.  **权力下放禁止铁律**：低层调度器 (L1/L0) 绝不能持有或私自创建高层调度器 (L3/L2)；所有依赖必须自上而下通过构造函数注入。
3.  **多线程独裁铁律**：全项目除 `L3` 的专属目录外，任何地方出现 `std::thread`、`QThread` 等线程创建代码，即视为架构违规。
