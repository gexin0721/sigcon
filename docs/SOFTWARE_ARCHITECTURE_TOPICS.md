# 软件架构确认与待定问题

## 当前确认的规则

本文件只讨论 `sigcon` 的软件部分，暂不扩展到硬件、固件实现细节、论文材料与非软件交付内容。

当前已经确认的规则如下：

- 软件主控制链保持单向：`UI <-> 调度 <-> 业务`
- `UI` 不知道业务实现，业务不知道 `UI` 存在
- `UI` 与业务不能直接交互，只能由调度层组织连接
- 调度层是唯一合法的编排层
- 架构禁止三角依赖
- 架构禁止菱形依赖
- 系统依赖必须尽量保持无环，禁止横向穿透破坏主控制链
- 一份核心状态不能被多条路径并行主写
- 一个核心实例不能被多个装配入口重复创建和并行管理

## 当前确认的思路与框架

当前确认的思路不是只有三大模块本身，而是先明确主控制链，再补齐支撑域。

### 1. 主控制链

- `UI`：负责展示、交互、页面状态呈现
- 调度层：负责实例创建、流程编排、线程切换、错误转译、状态协调
- 业务层：负责业务规则、领域逻辑、数据处理、外部能力调用编排

### 2. 当前确认的框架理解

- 三大模块是软件主干，不是软件全部
- 目录结构必须服务于职责边界，而不是反过来决定架构
- 主控制链之外，软件还必须补齐支撑域，否则架构是不完整的

### 3. 当前已识别的支撑域

- 资源文件
- 配置文件
- 缓存文件
- 日志文件
- 导出文件
- 工具代码
- 公共常量
- 共享状态
- 运行时上下文

### 4. 当前确认的框架目标

- 主控制链清楚
- 依赖方向清楚
- 状态归属清楚
- 装配入口清楚
- 异常兜底链清楚
- 支撑域归属清楚

### 5. 四层调度理论 `L0 ~ L3`

当前确认，调度层不是单一平面结构，而是采用树状分工的四层调度理论。  
其核心不是“层数越多越好”，而是每一层只承担自己那一级的调度责任，避免职责混杂、重复装配和越级控制。

#### 5.1 核心原则

- 调度层内部采用树状结构，上层负责组合，下层负责执行
- `L0 ~ L3` 的职责必须逐级放大，不能反向侵入
- `UI` 与业务仍然不能直接互相调用，必须通过对应层级的调度单元连接
- 越底层的调度单元越要求结果唯一、返回唯一、职责极简
- 越高层的调度单元越负责装配、编排、生命周期和全局协调
- 底层不允许创建多线程，多线程创建权只允许存在于 `L3`
- 低层不能偷偷承担高层职责，例如 `L0/L1/L2` 不得私自接管应用生命周期或全局线程资源

#### 5.2 `L0`：最小逻辑单元

`L0` 是最小调度颗粒，负责一次性、结果唯一的基础调度动作。

- 负责最基础的调度行为，例如弹窗、抖动、单次状态切换、单次结果确认
- 返回值必须唯一，结果必须明确，不允许形成多出口语义
- 允许自带极简的基础 `UI` 逻辑和基础业务逻辑
- 适合作为被复用的叶子节点，被 `L1/L2/L3` 调用

`L0` 不应承担的职责：

- 不负责窗口级装配
- 不负责完整业务流程编排
- 不负责应用级生命周期
- 不允许创建多线程

#### 5.3 `L1`：最小功能单元

`L1` 负责整合业务模块和 `UI` 模块，形成可以独立存在的单一窗口或单一功能界面单元。

- 负责一个窗口、页面或功能面板的调度闭环
- 负责把页面交互转成业务调用，再把结果转成页面状态
- 允许组合多个 `L0`
- 适合作为页面级、窗口级、功能级调度器

`L1` 不应承担的职责：

- 不负责跨多个业务域的大流程装配
- 不负责整个软件的生命周期
- 不允许创建多线程

#### 5.4 `L2`：最小业务单元

`L2` 负责整合多个 `L1`，或整合其他业务模块与辅助 `UI` 模块，形成一个相对完整的业务单元。

- 负责一个业务域内的多步骤流程编排
- 负责多个 `L1` 之间的协作、切换与状态协调
- 允许组合业务模块、辅助 `UI` 模块和多个 `L1`
- 适合作为模块级、业务域级调度器

`L2` 不应承担的职责：

- 不负责整个软件的总装配
- 不负责应用级生命周期收口
- 不允许创建多线程

#### 5.5 `L3`：最小软件单元

`L3` 是最小软件级调度单元，负责整合多个 `L1` 与 `L2`，完成整个软件层面的装配与控制。

- 负责整个软件的总体布局和总装配
- 负责应用启动、运行、退出等生命周期管理
- 负责全局级状态协调与总入口控制
- 负责多线程的创建、持有、回收和统一约束
- 负责定义底层任务如何安全回到主线程

`L3` 是唯一允许创建多线程的层级。  
这意味着线程、线程池、后台任务对象、主线程回投入口等能力，原则上都应由 `L3` 统一提供或统一托管。

#### 5.6 层间关系与禁止事项

- 合法主链为：`L3 -> L2 -> L1 -> L0`
- `L3` 可以按装配需要直接组合多个 `L2`，也可以直接挂接必要的 `L1`
- `L2` 可以组合多个 `L1` 和必要的 `L0`
- `L1` 可以组合多个 `L0`
- 低层不能反向拥有高层
- 低层不能绕过中间层直接承担更高一级职责
- 一个核心实例只能有一个明确拥有者，避免多入口重复装配
- 一个核心状态只能有一个主写路径，避免并行主写
- 底层不允许创建多线程，避免线程模型失控和 `UI` 主线程约束被破坏

## 仍需继续细化的问题

### A. 异常管理

#### 当前已确认的规则

- 异常主分类按技术模块或业务模块划分，不按抽象职责划分
- 所有模块异常统一继承顶层异常基类，由顶层统一异常入口做总收口
- 模块内部允许继续细分二级异常，例如参数错误、超时、资源缺失、任务失败等
- 是否记录日志、是否提示用户、是否允许重试等处理策略，应依赖统一异常元信息，而不是只依赖类名硬编码

#### 当前分析的问题

- 异常主分类如何按模块边界划分，例如 `UI`、调度、网络、存储、线程、业务域各自如何归属
- 是否需要统一错误码体系
- 是否需要统一异常基类、统一结果类型，还是两者并存
- 哪一层负责统一接住异常，尤其是调度层与业务层之间的责任边界
- `HTTP` 超时、参数错误、资源缺失、后台任务失败、未知异常是否采用同一套反馈机制
- 用户提示、开发日志、诊断信息是否需要三层分离
- 某个局部模块失败后，如何保证失败停留在局部，不放大为全局崩溃

#### 需要继续确认

- 模块清单与异常归属规则
- 模块内二级异常的拆分方式
- 异常分级方式
- 错误码是否启用
- 统一异常入口放在哪一层
- 统一日志入口放在哪一层
- 页面级恢复、模块级恢复、应用级恢复如何区分

### B. 多线程与创建权

#### 当前已确认的规则

- 多线程创建权只属于 `L3`
- `L0/L1/L2` 不允许创建多线程
- `worker`、线程池、异步任务对象、主线程回投入口，原则上由 `L3` 统一提供或统一托管
- 线程相关能力属于调度层高层能力，不下放到底层调度单元

#### 需要继续细化

- 后台任务取消、超时、重试由谁负责
- 线程资源释放和异常收口由谁负责
- 页面关闭后，后台任务是中止、托管还是转后台继续执行
- `L3` 对线程能力的暴露形式，是统一任务接口、统一任务总线，还是统一线程服务

### C. 调度层的组合与装配归属

#### 当前已确认的规则

- 调度层内部存在明确层级，不再视为单层结构
- 页面级、功能级调度单元归入 `L1`
- 模块级、业务域级调度单元归入 `L2`
- 应用级总调度器或应用装配根归入 `L3`
- 调度器不能由页面随意自行创建，创建权必须服从上层装配关系
- 调度层既承担编排职责，也承担本层应有的装配和生命周期职责

#### 需要继续细化

- 调度器的创建规则
- 调度器的持有规则
- 调度层与依赖注入边界如何划分
- 一个业务服务被多个 `L2` 或 `L3` 使用时，如何避免再次形成菱形依赖

### D. 资源、数据与公共能力归属

#### 当前分析的问题

- 静态资源、运行时数据、配置、缓存、日志、导出文件是否各自独立管理
- 工具代码和基础设施代码如何区分
- 公共常量、枚举、错误码、协议键名、配置键名是否集中管理
- 共享状态与全局变量如何严格区分
- 是否允许存在“公共变量区”，还是只允许“公共常量区”和“共享状态区”
- 后续目录结构如何映射这些归属规则

#### 需要继续确认

- 各类文件的归属规则
- 工具与基础设施的边界
- 共享状态的拥有者规则
- 公共常量与运行时共享状态的拆分方式

## 当前结论

当前已经确认的，不再是“哪些问题要不要讨论”，而是以下基础规则：

- 主控制链必须单向
- `UI`、调度、业务不能形成三角
- 整个依赖拓扑不能形成菱形
- 调度层必须承担唯一合法编排职责
- 调度层内部采用 `L0 ~ L3` 四层树状结构
- `L0` 是最小逻辑单元，`L1` 是最小功能单元，`L2` 是最小业务单元，`L3` 是最小软件单元
- 多线程创建权只属于 `L3`，`L0/L1/L2` 一律不得创建多线程 

当前真正尚未确定的，是这些规则如何继续细化到：

- 异常管理机制
- `L3` 内部线程能力的具体管理方式
- 调度器的创建、持有与依赖注入细则
- 资源、数据、日志、配置、工具与共享状态的归属方式

后续如果继续展开讨论，应优先围绕上面的 `A/B/C/D` 四个待定问题深入，而不是重新回到已确认规则本身。
