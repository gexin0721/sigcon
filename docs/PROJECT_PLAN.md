# 项目总计划

## 1. 先回答三个问题

### 1.1 做什么
在正式开发前，先整理 `sigcon` 项目的整体构造、模块边界、开发顺序与约束，避免后续在桌面端、固件端、文档端同时推进时出现方向漂移和重复返工。

### 1.2 怎么做
先以仓库现状为基线，确定项目级目录职责，再细化 `desktop` 的三大模块架构：业务、UI、调度；随后按阶段推进基础骨架、共享协议、桌面端、固件端、联调与测试。

### 1.3 为什么
当前仓库已经有基础骨架，但仍处于“可以开始实现、尚未统一结构”的阶段。如果此时直接进入功能开发，后续很容易出现目录混乱、依赖反向、线程模型不清晰、测试位置不统一等问题。

## 2. 当前仓库现状

当前仓库已经存在以下一级目录：

- `desktop/`：Qt 桌面端，当前只有最小可运行窗口骨架
- `firmware/`：ESP32 固件工程，已有一定的硬件与系统代码
- `hardware/`：硬件相关资料目录
- `docs/`：文档目录，当前有 `api/`、`diagrams/`、`thesis/`
- `scripts/`：本地构建、运行、打包脚本
- `tests/`：仓库级测试目录

当前仓库说明文件中还规划了以下目录，但尚未看到实体目录：

- `shared/`：共享协议与共享模型定义
- `runtime/`：运行期日志、缓存、导出数据

结论：

- 仓库已经具备“多端协同项目”的基本雏形
- 当前最缺少的是项目级结构约定，而不是继续新增零散代码
- 下一步应先统一结构与阶段计划，再进入持续开发

## 3. 项目总目标

`sigcon` 的目标不是单一程序，而是一个由多部分组成的工程项目：

- 固件端：负责设备控制、传感器采集、控制逻辑、对外服务
- 桌面端：负责监控、配置、调度、状态展示、事件查看
- 协议与共享模型：负责桌面端和固件端之间的数据契约
- 文档与脚本：负责工程落地、构建、测试、答辩材料和交付流程

项目的阶段性成果不应只看“程序能不能跑”，还要看：

- 模块边界是否清晰
- 线程与调用关系是否稳定
- 测试与文档是否跟得上
- 后续是否便于扩展和答辩展示

## 4. 建议的仓库级结构目标

建议将仓库逐步稳定为如下结构：

```text
sigcon/
├─ desktop/        # Qt 桌面端
├─ firmware/       # ESP32 固件端
├─ shared/         # 协议、DTO、共享枚举、状态码
├─ hardware/       # 原理图、PCB、BOM、导出物
├─ docs/           # 架构、接口、图表、论文材料、计划
├─ scripts/        # 构建、运行、打包、测试脚本
├─ tests/          # 仓库级集成测试与联调测试
└─ runtime/        # 运行期日志、导出物、缓存
```

说明：

- `desktop/` 和 `firmware/` 是主实现域
- `shared/` 是后续非常关键的一层，避免协议定义两边各写一套
- `tests/` 放仓库级测试；模块内部测试则优先跟随模块自己的 `test/`
- `runtime/` 不建议提交业务数据，只保留占位与忽略规则

## 5. desktop 端的架构原则

`desktop` 不建议简单地理解为“一个 `src` 加一个 `include`”。  
推荐先按职责切，再讨论目录细节。

### 5.1 三大模块

建议桌面端按以下三大模块拆分：

- 业务模块：负责业务规则、数据模型、设备状态、协议适配、数据处理
- UI 模块：负责窗口、页面、控件、资源、样式与用户交互展示
- 调度模块：负责流程编排、ViewModel、线程切换、命令分发、页面导航

### 5.2 三层对应关系

这三层可以理解为：

- 业务模块 = Model
- UI 模块 = View
- 调度模块 = ViewModel + Application Coordinator

因此这里的 MVVM 不是被 Qt 框架限制出来的目录名，而是一种职责边界：

- UI 只负责展示和交互
- 业务只负责规则和数据
- 调度负责把 UI 输入转为业务调用，再把业务结果转为 UI 状态

### 5.3 Qt 约束必须前置写清

由于 Qt 的 QWidget/UI 操作必须在主线程执行，因此桌面端必须明确以下规则：

- UI 控件只能由主线程操作
- 业务层不能直接持有 UI 控件
- 后台线程不能直接更新界面
- 所有回到 UI 的动作都必须经过调度层提供的主线程提交接口

后续在 Qt 中可通过以下方式落地：

- `signal/slot`
- `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`
- `QObject` 线程归属
- `QThread` 或 `QThreadPool`

## 6. desktop 目录规划建议

桌面端建议逐步从当前最小骨架调整为如下结构：

```text
desktop/
├─ CMakeLists.txt
├─ app/
│  └─ main.cpp
├─ business/
│  ├─ include/
│  └─ src/
├─ ui/
│  ├─ include/
│  ├─ src/
│  └─ resources/
├─ scheduler/
│  ├─ include/
│  └─ src/
├─ lib/
├─ test/
└─ cmake/
```

各目录职责如下：

- `app/`：程序入口、启动装配
- `business/`：业务逻辑、模型、设备状态、协议适配
- `ui/`：窗口、页面、控件、QSS、图标、字体、图片
- `scheduler/`：ViewModel、导航、消息分发、线程桥接、任务调度
- `lib/`：手工接入的预编译第三方库
- `test/`：桌面端测试文件，统一放这里，不再创建子测试目录
- `cmake/`：辅助 CMake 脚本

## 7. 资源、头文件、库、测试、额外模块的放置规则

### 7.1 资源文件

统一放在 `desktop/ui/resources/`，例如：

- 图标
- 图片
- 字体
- QSS
- Qt 的 `.qrc` 文件

### 7.2 头文件

按模块归属管理，不建议所有头文件堆在一个公共目录：

- 模块对外接口头文件放在各模块自己的 `include/`
- 模块内部实现相关头文件可以和实现一起放在 `src/`

### 7.3 库文件

需要区分来源：

- 自研功能模块：优先做成 `business`、`ui`、`scheduler` 的子库或子目标
- 第三方源码库：后续可单独规划 `third_party/`
- 预编译库：先放 `desktop/lib/`

### 7.4 测试文件

按当前约束，桌面端测试统一放在 `desktop/test/`，不要在其下再建子目录。

### 7.5 额外模块

不要额外建“杂项模块区”，而是按职责归入三大模块：

- 业务相关扩展，放入 `business/`
- 页面与控件扩展，放入 `ui/`
- 导航、线程、命令、状态编排扩展，放入 `scheduler/`

## 8. shared 层的规划建议

`shared/` 建议尽早建立，因为桌面端和固件端迟早要共享协议定义。

`shared/` 后续可以承担：

- 协议字段定义
- 状态码与错误码
- 通信消息体说明
- 配置项键名
- 设备状态枚举

注意：

- 若桌面端与固件端语言不同，共享层不一定直接共享源码
- 但至少要共享“协议真源”，避免一边改了另一边不知道
- 最差也应共享文档、OpenAPI、数据样例和版本号规则

## 10. 当前已知风险与待确认项

### Q1 当前文档与实体目录不一致

仓库 `README.md` 中提到了 `shared/`、`runtime/`，但当前尚未看到对应目录。  
这不是立即阻塞问题，但如果继续实现而不补齐，后续容易造成说明与实际不一致。

### Q1 桌面端当前仍是最小骨架

当前 `desktop` 仅有一个最小 Qt Widgets 入口，尚未建立业务、UI、调度边界。  
如果直接在当前 `src/` 下继续追加功能，后续会提升返工概率。

### Q1 线程模型尚未文档化

你已经明确指出 Qt 的 UI 主线程限制，这一点必须在后续架构文档与代码层共同落地。  
如果先写功能再补线程规则，后面会出现跨线程更新 UI 的隐患。

## 11. 下一步建议

建议按以下顺序继续推进：

1. 先确认本计划文档是否接受
2. 再补一份 `docs/desktop_architecture.md`，专门细化桌面端三层架构
3. 然后再开始调整 `desktop` 的目录和 CMake
4. 最后再进入具体功能开发

本文件是“总控计划”，不替代后续的模块设计文档、接口文档和测试文档。
